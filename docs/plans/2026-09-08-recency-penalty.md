# 連続出場を少し嫌う（目的8 `recency`）

2026-09-08

## 背景

2026-09-08 の実データ（20人3コート・38試合）を分析したところ、**試合数の偏りは小さい
のに待ち時間の偏りが大きい**ことが分かった。

- 試合数: 6〜9（平均 7.6、幅 3）。前半19試合は全員3〜4回でほぼ完璧に均等
- 待ち: 「自分が出ていない間に行われた試合数」の最大が **11 試合**（3コートなので
  実時間で 25 分以上）の人が4人。一方で空き1〜2試合で回り続ける人もいる
  - みっちゃん: 空き `2,2,1,2,2,2` ＝ ほぼ連続（遅参加のキャッチアップ。正しい挙動）
  - すぎ / みさと: 空き `3,3,6,11,6` / `6,6,3,11,3` ＝ 一度も連続出場が無い

bench（`scripts/bench-court-assignment.ts`、本番エンジン `ENGINE=objective`、
21人3コート・13ラウンド・NOISE=4・30シード）でも現状は

```
試合数幅 1.37 / 待ち 9.53
```

で、**9〜10 試合待ちは設計どおり出る**（同日に直した自動終了バグとは別の構造的な話）。

原因は明確で、**配置の判断材料に「前回出場からの経過」が一切無い**こと。

- `calculatePriorityScore`（`algorithm.ts`）＝ 試合数（待機時間優先モードなら
  試合数 ÷ 滞在分）。経過時間は見ない
- 目的関数の目的2 `waiting` は名前に反して経過時間ではなく
  「優先度順位（＝試合数の順位）が最上位の人を控えに回していないか」
- `lastPlayedAt` を実際に使っているのは**シングルスのペアコストだけ**
  （`SINGLES_WEIGHT_RECENCY = 500`「直前プレイ者を含むペアは最優先で回避」）。
  ダブルスにだけ同等の仕組みが無いという非対称になっている

結果、試合数が並んだ人の中では、多様性・男女構成・序列差だけで選ばれる。
**回数は揃うが待ちは揃わない。**

## 方針

「長く待った人を優先」ではなく「**直前に出た人を少し嫌う**」として入れる。

| | 優先度スコアに待ち時間を入れる | 目的関数に `recency` 項を足す（採用） |
|---|---|---|
| 効き方 | 候補全体の並び順が変わる | 直前に出た人だけを弱く減点 |
| 試合数の均等 | 壊れうる（8試合の人が10分待てば6試合の人を追い越す） | 優先度順位を動かさないので保たれる |
| 遅参加のキャッチアップ | 弱まる | 重みを `fairness` 未満にすれば維持される |
| 前例 | なし | シングルスに実装済み |

## 設計

### 1. 指標（`objective.ts`）

**時刻ではなく試合履歴ベース**にする。`Date.now()` に依存すると bench が
非決定的になり、実運用でも端末の時計差に影響されるため。

```
gapOf(id)  = その人が最後に出場した試合から数えて経過した試合数
             （直前の試合に出ていた = 0、1試合はさんだ = 1、未出場 = ∞）
recency(id) = max(0, 1 − gapOf(id) / RECENCY_SPAN)
term        = 配置された全員の recency の平均（0〜1・小さいほど良い）
```

- `RECENCY_SPAN` は **コート数**（最低1）。3コートなら「1巡（3試合）休めば 0」。
  コート数で割ることで、面数が変わっても「1巡ぶん」の意味が保たれる
- 未出場（`gapOf = ∞`）は 0。初回保証（`gamesPlayed === 0` の `-Infinity`）と
  衝突しない
- 練習開始直後は履歴が空で全員 0 になり、この項は何もしない

### 2. 配線

- `ObjectiveWeights` / `ObjectiveTerms` に `recency` を追加し、
  `computeObjectiveTerms` / `weightedObjective` に1行ずつ足す
- `ObjectiveInput` に `recencyById: Map<string, number>`（値は `gapOf`）を追加
- `AssignRoundParams` に同じものを追加して素通しする（省略時は空 Map ＝ 無効）
- `algorithm.ts` は `assignCourts` が受け取っている `matchHistory` から
  `gapOf` を1回だけ組み立てて渡す（末尾から走査。O(履歴長)）
- **旧エンジン（`useObjectiveEngine: false`）は触らない**

### 3. 重み

`DEFAULT_WEIGHTS.recency` を bench で決める。制約は **`fairness`(1.5) 未満**
（超えると遅参加のキャッチアップより連続回避が勝ってしまう）。

bench で `RECENCY_WEIGHT` 環境変数からこのプロセス内だけ上書きできるようにする
（`AFFINITY_WEIGHT` と同じ仕組み）。

## 決め方（bench）

```bash
ENGINE=objective SEEDS=30 NOISE=4 CONDITIONS=21x3 ROUNDS=13 \
  RECENCY_WEIGHT=0 npx tsx scripts/bench-court-assignment.ts
# 0 / 0.2 / 0.4 / 0.6 / 0.9 / 1.2 を振る
# 採用値が決まったら SEEDS=100・全条件（既定 CONDITIONS）で確認
```

現状値（21人3C・NOISE=4・SEEDS=30）: `試合数幅 1.37 / 待ち 9.53`

**合格条件**:

| 指標 | 目標 |
|---|---|
| 待ち（目的2） | 9.53 → **7.5 以下** |
| 試合数幅（目的1） | 1.37 から **+0.2 以内** |
| 占有率% / 共演（目的6） | 悪化 5% 以内 |
| 幅広% / 競り度 / 3-1%（目的3〜5） | 誤差範囲（±1pt 程度） |

**最大のリスクは目的6（多様性）の悪化**。20人3コートは待機が8人しかいないため、
直前組4人を嫌うと「残り4人」がほぼ確定してしまい、同じ顔ぶれが繰り返される
おそれがある。占有率%・共演が悪化するようなら重みを下げる。それでも両立しない
場合は採用を見送る（待ちのために多様性を売らない）。

## 計測結果

**結論: 採用見送り（`DEFAULT_WEIGHTS.recency = 0`）。**
実装・テスト・bench の口（`RECENCY_WEIGHT`）は入れたが、**合格条件「待ち 7.5 以下」を
満たす重みが存在しなかった**ため、既定では無効（この項が常に 0）にしてある。
「待ちのために多様性を売らない」という上の方針に従った判断。

### 制約を無視して重みを上げた場合（SEEDS=30）

| 重み | 待ち | 試合数幅 | 占有率% | 共演 | 3-1% |

plan が想定していた「多様性が悪化するなら見送り」の分岐にそのまま該当する。

### なぜ効かないのか（構造的な理由）

待ち（目的2 の bench 指標）の内訳を計測したところ:

```
w=0: 待ち 9.53 ＝ 途中の空きの最大 9.23 / 末尾の待ちの最大 7.40 / 途中の空きの平均 4.18
```

**21人3コートでは出場間隔の平均がそもそも 4.18 試合**（1試合で 21人中4人しか出ない
ので 21/4 − 1 ≈ 4.25 が理論値）で、待ち 9 台はその分布の**裾**でしかない。
一方この項が区別できるのは `gapOf < RECENCY_SPAN`（＝コート数 3）の範囲、つまり
**平均間隔より短い側だけ**。「直前に出た人を弱く減点する」ことはできても、
「8試合待っている人」を引き上げる力を原理的に持たない。

`RECENCY_SPAN` を 5 / 6 / 8 に広げて測っても（＝より長く休んだ人まで区別しても）:

| span / 重み | 待ち | 試合数幅 | 占有率% | 共演 | 3-1% |
|---|---|---|---|---|---|
| 5 / 1.2 | 8.93 | 1.17 | 40.0 | 13.69 | 3.8 |
| 5 / 3 | 8.50 | 1.23 | 40.3 | 13.45 | 4.4 |
| 5 / 8 | **7.87** | 1.23 | 42.3 | 13.10 | **6.5** |
| 6 / 8 | 7.93 | 1.23 | 42.3 | 13.28 | 6.1 |
| 8 / 8 | 8.07 | 1.23 | 41.7 | 13.26 | 4.4 |

7.5 には届かず、7.9 まで下げた時点で 3-1% が +2.5pt（許容 ±1pt）、占有率が +5.5%
（許容 5%）と条件を超える。**指標の定義（＝セッション中の最大値）を変えない限り、
この形の項では合格条件に到達できない。**

### bench と本番の履歴セマンティクスのズレ（要注意・未解決）

計測中に見つかった**設計上の穴**。`gapOf` は `matchHistory` の並びから数えるが、
その中身が bench と本番で違う。

- **本番**: `matchHistory` に積まれるのは**終了した試合だけ**（`gameOperations.ts` の
  `updatedMatchHistory = [...state.matchHistory, match]` は終了時）。コートが1面
  空いた瞬間、そこから降りた4人は履歴の末尾 ＝ `gapOf = 0`（recency 1.0）。
  その前の終了分が 1、さらに前が 2 で、**直近3回の終了ぶん（12人）に段階的な信号**が付く
- **bench**: `history.push` が**配置時**なので、進行中の試合も履歴に入っている。
  コートが空いた瞬間、降りた4人は既に `gapOf = コート数−1 = 2`（recency 0.333）で、
  gap 0 / 1 に該当するのは**他コートで進行中＝候補ですらない人**。
  つまり **bench では「降りたばかりの4人を 1/3 の強さで嫌う」だけの項として測られる**

したがって bench は本番より **この項を弱く見積もる**。上の重み振りをそのまま本番の
較正値として使うと効きすぎる可能性がある（今回は採用しないので実害は無いが、
将来この項を有効化するときは bench 側の履歴を終了順に直してから測り直すこと）。
なお `RECENCY_SPAN` を広げた計測（上の表）は本番相当の届き方を近似したものだが、
それでも合格条件には届かなかったので、見送りの結論はこのズレに依存しない。
