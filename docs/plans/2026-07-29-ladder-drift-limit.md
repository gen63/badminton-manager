# ハシゴ式の `maxDrift` 制限は緩めても効果なし（不採用）

2026-07-29

## 発端

`applyStreakSwaps`（ハシゴ式）の `maxDrift = stepSize`（元の序列から離れてよい
上限は1グループ分）というハード制限は、`docs/plans/2026-07-28-skill-gap-separation.md`
で「無制限だと上位者が下位グループまで沈み、グループ内の実力幅が広がる
（18人3コートで 5 → 10.5）」という理由で入れた。

**この根拠の計測が循環していた疑いがあった。** 「グループ内の実力幅」を
`player.rating`（手動序列）を正解とみなして測っていたため、序列を動かす仕組み
（ハシゴ式）は勝敗で人を動かした時点で必ず「正解」から離れ、悪化して見える。
これでは「ハシゴ式が間違っている」のか「ハシゴ式は正しくて序列が古いだけ」なのか
区別できない。

`scratchpad/truth.ts`（各プレイヤーに **真の実力** を持たせ、`player.rating` は
それにノイズを乗せた写しとし、勝敗は真の実力から Bradley-Terry で確率的に決め、
分離は真の実力基準で測るハーネス）で、この循環を排除して検証した。

仮説: 「序列が正確（NOISE=0）なら制限は正しいかもしれないが、序列がズレている
（NOISE=4/8）ときにハシゴ式が勝敗から補正してくれるなら、制限は緩めるべき」。

## 結論: 不採用（緩めても改善しない。悪化する）

**`maxDrift` を緩めても、NOISE=0/4/8 のいずれでも真の実力基準の分離は改善しない。**
2コートは無反応、3コートは緩めるほど単調に悪化する。判定基準（NOISE=4/8 で有意
改善・NOISE=0 で悪化しない）のどちらも満たせず、`src/lib/algorithm.ts` は
変更していない（`maxDrift = stepSize` のまま）。

**そもそも分離が改善しないので緩める理由がない。**

### 何が起きているか

- **2コート（13/14/16人）は `maxDrift` を何倍にしてもほぼ無反応**（誤差1シード
  分程度の揺れのみ）。2コートの上位×下位同居のハード制約
  （`hasTopBottomExtremes`、`selectBestFour` / `splitBestTwoCourts` から呼ばれる）
  は `baseRankById`（`buildInitialOrder` そのまま、ハシゴ式適用前の序列）で判定
  しており、`applyStreakSwaps` の出力に依存しない。`maxDrift` が効くのは
  `groupPlayers3Court`（3コート以上のグループ分け）と `formTeams` のペア決定
  だけなので、2コートでは変化のしようがない。
- **3コート（15/18人）は緩めるほど単調に悪化**。これは NOISE=0（序列が完全に
  正確）でも同じ方向に起きている。つまり「序列が古いから起きる悪化」ではなく、
  「勝敗そのものに確率的なブレがある（Bradley-Terry なので実力差があっても
  逆転勝ちする）ため、ドリフト幅を広げるほど**その場限りの連勝・連敗**で
  グループが動きすぎて、真の実力から見て不適切な組み合わせが増える」ため。
  ハシゴ式は回転装置として機能する一方、動ける幅が広いほど「たまたまの連勝・
  連敗」に振り回されるノイズも増幅する。序列のズレ（NOISE）を大きくしても
  この構造は変わらないため、NOISE=4/8 でも改善が発生しない。
- 元の `maxDrift = stepSize` というコメントの根拠（「無制限だと上位者が
  下位グループまで沈み、グループ内の実力幅が広がる」）は、**手動序列基準の
  計測は循環していたが、結論自体（緩めると悪化する）は真の実力基準でも
  そのまま成立する**。循環していたのは計測方法であって、結論は正しかった。

### 従来ハーネス（序列基準）でも参考として確認

`focus.ts` / `gbench.ts` / `seq_holistic.ts` は `player.rating` を正解として
分離を測るため、ハシゴ式を動かす変更は原理的に悪化して見える
（`docs/plans/2026-07-29-sequential-skill-separation.md` と同じ注意点）。
今回は変更しない結論のため、これらでの追加確認は不要と判断した。

## 検証方法

`scratchpad/truth.ts`（各プレイヤーに真の実力 `trueRank` を持たせ、
`player.rating` は `trueRank + ノイズ(±NOISE順位)` をソートし直した写し。
勝敗は `trueRank` から Bradley-Terry で確率的に決定。分離は `trueRank` 基準で
測る）を使用。`SEEDS=150`、`NOISE ∈ {0, 4, 8}`、人数・コート数は
`[13,2], [14,2], [16,2], [15,3], [18,3]` の5条件、`mode='mixed'`（コート終了
時刻が最大60秒ずれるまで同時扱いする現実的な混在パターン）。

`maxDrift` の値を `src/lib/algorithm.ts` 内で直接書き換えて
（`stepSize` → `stepSize*1.5` → `stepSize*2` → `Infinity`）都度計測し、
最後に `git checkout -- src/lib/algorithm.ts` で HEAD の状態
（`maxDrift = stepSize`）に戻した。

## 完了条件と実施内容

- `src/lib/algorithm.ts` は変更していない。`git diff` はクリーン
  （HEAD と完全一致、`maxDrift = stepSize` のまま）
- コードを変更していないため `npm run build` / `npm run lint` /
  `npm run test:run` の再実行・ユニットテスト追加は対象外
- 上記の否定的結果を本 plan に記録した（同じ検証を将来繰り返さないため）

## 今後の選択肢（未着手）

- 3コートの分離をさらに改善したい場合、`maxDrift` を動かす方向ではなく、
  `getSkillGapPenalty` の重み（`SKILL_GAP_WEIGHT`）や `hasIsolatedExtreme` の
  バンド幅など、**`baseRankById`（ハシゴ式適用前の序列）を使う既存の仕組み**を
  調整する方が筋が良い可能性がある（`applyStreakSwaps` の出力に依存しないため、
  2コートと3コートで一貫した効果が期待できる）
- 序列の陳腐化そのものへの対処は `docs/plans/2026-07-29-adaptive-skill-ranking.md`
  （実測レートを混ぜる案）で別途検証済み・不採用。今回の結果と合わせると、
  「序列のズレを勝敗から補正する」という方向自体、少なくとも今回試した2つの
  切り口（実測レートの混合／ハシゴ式のドリフト拡大）ではどちらも効果が
  確認できていない
