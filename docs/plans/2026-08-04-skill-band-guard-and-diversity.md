# 3コートの実力帯ガード漏れの修正と、帯内の多様性強化

2026-08-04

## 発端

2026-08-04 のセッション（21人3コート、44試合）で、**げん・りょーや（序列20位・21位）
から「同じメンバーとの試合が多い」という感想**が出た。

組み合わせを実データで検証したところ、2つの別々の問題が見つかった。

### 問題A: 上位×下位の同居ガードが3コートで効いていない

素のレート序列で「上位帯（1-7位）3人＋下位帯（15-21位）1人」の試合が **4件**あった。
全てリュカ（19位）が上位帯3人と同居したもの。

| 試合 | メンバー（括弧内は素の序列） | レート差 |
| --- | --- | --- |
| 第7 | つっきー(1) ゆーや(2) きゃん(4) リュカ(19) | 15.9 |
| 第11 | テリー(5) まも(6) うめみや(7) リュカ(19) | 12.8 |
| 第23 | つっきー(1) ゆーや(2) きゃん(4) リュカ(19) | 15.9 |
| 第26 | ゆーや(2) きゃん(4) うめみや(7) リュカ(19) | 14.9 |

全44試合のレート幅は中央値 8.2 / 最大 15.9 で、この4試合だけ突出している。
第7と第23は**同一4人の再演**でもある。

**原因**は `src/lib/algorithm.ts` の2点:

1. `selectBestFour` の `isValidBase`（algorithm.ts:1414）で3コート以上が使う
   ハード制約は `hasIsolatedExtreme(ids, groups3)` だが、`groups3` は
   `groupPlayers3Court` の出力＝**`applyStreakSwaps`（ハシゴ式）適用後**の序列で
   作られる。リュカは序盤の勝利で `maxDrift = stepSize = 7` ぶん上がって upper
   グループの正規メンバーになったため、このガードから見れば「上位の人」であり
   何も弾かれない。
2. 素の序列（`baseRankById`）で判定する `hasTopBottomExtremes` は
   `hasSkillGapHardConstraint = totalCourtCount === 2 && !!baseRankById`
   （algorithm.ts:1430）と**2コート限定**で、3コート以上では一切呼ばれない。

ソフトな `getSkillGapPenalty` は素の序列で見るので本来は重いペナルティ
（gap=18, allowance=7 → `SKILL_GAP_WEIGHT * 0.846 ≒ 1.69` × oneGameDelta）が
付くはずだが、**そのコートの候補プールが upper グループ全員なので全候補が同程度の
ペナルティを負い、順位づけに差がつかず実質無力化される**。ハシゴ式でグループに
入れられた時点で勝負がついている。

なお `docs/plans/2026-07-29-ladder-drift-limit.md` の「今後の選択肢」は、
「3コートの分離を改善したいなら `maxDrift` ではなく `baseRankById` を使う既存の
仕組み（`SKILL_GAP_WEIGHT`、`hasIsolatedExtreme` のバンド幅）を調整する方が筋が
良い」と既に指摘していた。本 plan の変更1はその線に沿う。

### 問題B: 下位帯の不満の実体は「人数」ではなく「回数の偏り」

> **注意: この節の指標選びは的外れだった。**
> 「共演人数」を指標に変更3・4 を進めたが、どちらも共演人数を分離と交換するだけで
> 頭打ちになった。体感に効くのは共演人数ではなく**特定の1人が自分の試合に占める割合
> （占有率）**で、しかも既存のペナルティが**合計ベース**なのでその偏りを検出できて
> いなかった。これを直したのが変更5。後述の「実データの再分析」と変更5 を読むこと。
> 以下は経緯として残す。

隣接帯まで許容した場合の理論上の共演可能人数を実データで計算した:

| | 実際の共演人数 | 隣接帯まで許容した上限 | 全体 |
| --- | --- | --- | --- |
| げん | 13人 | **13人** | 20 |
| りょーや | 10人 | 13人 | 20 |
| あすか | 11人 | 13人 | 20 |
| みずき | 12人 | 13人 | 20 |

**げんは既に上限に到達している。** つまり「上位と組めていない」のは設計どおりで
あって異常ではない。実際の不満の源は回数の偏りの方:

- げん × りょーや **4回**（げん8試合・りょーや7試合中）
- あすか × 美玖 **5回**、あすか × みずき **5回**
- りょーやの**パートナー**は7試合で5人だけ（みずき2・あお2・美玖1・あすか1・まーや1）

したがって **「未共演を優先する」ことで上位×下位を組ませる必要はない**。多様性は
実力帯を跨ぐ動機にはならず、帯内・隣接帯の回数を平準化すれば足りる。

## 方針: 実力帯ガードを多様性より上の層に置く

多様性ロジックが実力分離を侵食しないよう、3層に分ける。

| 層 | 内容 | 性質 |
| --- | --- | --- |
| 1 | 素の序列での上位×下位同居の禁止 | **ハード制約** |
| 2 | `getSkillGapPenalty`（`SKILL_GAP_WEIGHT = 2.0`） | ソフト |
| 3 | 未共演ボーナス／ペア・組み合わせ重複ペナルティ | ソフト（上限は必ず 2.0 未満） |

多様性は**層1を通過した候補の中だけのタイブレーク**になる。これなら
「実力帯ごとの優先が意味をなくす」ことは構造的に起こらない。

## 変更内容（この順に1つずつ計測する）

### 変更1: `hasTopBottomExtremes` を3コート以上でもハード適用

`selectBestFour` の `hasSkillGapHardConstraint` から `totalCourtCount === 2` の
ゲートを外し、`baseRankById` があれば常に適用する。既存の3段階フォールバック
（「全部満たす」→「上下同居だけ緩める」→「上位4人」）はそのまま使えるので、
候補が枯れたときに待機者を飛ばす副作用は出ない。

バンド幅は3コート以上では `EXTREME_BAND`（3）と `SEQUENTIAL_EXTREME_BAND`（2）の
どちらが良いかを bench で決める。21人なら band=3 で「1-3位 × 19-21位」の同居禁止。

期待効果: リュカ型の4試合が消える。副作用として試合数幅（公平性）が悪化しうるので
必ず計測する。

（`WIDE_EXTREME_BAND_MIN_ROSTER = 18`）。15人3コートで band=3 にすると上下バンドが
ロースターの 40% を占め、試合数幅が +0.26 と重くなるため。

NOISE=8（序列が真の実力から大きくズレている）での改善幅が小さいのは当然で、
素の序列を信じるガードなので序列自体が誤っていれば的を外す。序列の陳腐化への
対処は別問題（`docs/plans/2026-07-29-adaptive-skill-ranking.md` で検証済み・不採用）。

#### ユニットテスト

`src/lib/algorithm.test.ts` の
`assignCourts - 3コート以上の逐次配置の実力分離 (hasTopBottomExtremes)` に追加。

再現には**双方向のドリフト**が要る。`maxDrift = stepSize = 7` なので21人では
下位者は 18→11 までしか上がれず、単独では上位グループに届かない。実データで
起きていたのは「上位者が連敗して 0→7 に沈み、下位者が連勝して 18→11 に上がり、
**中位グループで合流する**」パターンだった。そこでテストは「レート合計が低い側が
必ず勝つ」ラウンドを回す。

- 21人3コート50ラウンド（150試合）で上位3人×下位3人の同居が **2件以内**。
  ガードを外すと **8件**発生して落ちる（上限3件でアサート）

  当初は「0件」で固定していたが、変更3（`PAIR_REPEAT_PENALTY_CAP` の引き上げ）で
  選出が変わると 2 件出るようになった。ハード制約が破れたのではなく、選出順が
  変わった結果フォールバックが発火するラウンドに当たったため（bench 上の分離率は
  cap 0.2 / 0.6 のどちらも 0.8% で不変）。0件は**たまたま成立していた性質**であり、
  3段階フォールバックがある以上保証できないので、上限で固定する形に直した。
- 15人3コート（待機3人）では上下同居を完全に避ける組が存在しないラウンドが出る。
  既存の3段階フォールバックが上下同居の制約だけを緩め、例外にならず毎ラウンド
  3コート12人を配置しきることを固定した（待機者を飛ばさない設計の保証）

なお18人3コートも待機6人でフォールバックが働くため同居は 0 にならない
（150試合中3件、ガードなしでは19件）。21人と同じ性質で追加の情報が無いため、
テストは21人の1本に絞った。

### 変更2: `applyStreakSwaps` の `maxDrift` を狭める

`maxDrift = stepSize` → `Math.max(1, Math.ceil(stepSize / 2))`。

`docs/plans/2026-07-29-ladder-drift-limit.md` は **緩める方向**（1.5x / 2x / 無制限）
のみを計測し、3コートでは緩めるほど単調に悪化すると結論づけた。**狭める方向は
未検証**であり、その単調性からは改善が予測される。同 plan の「たまたまの連勝・
連敗でグループが動きすぎる」という説明とも整合する。

ただしハシゴ式はコート固定化を防ぐ回転装置なので、狭めすぎると回転（1人が複数の
コートを経験する度合い）が落ちる。**回転低下がないことを計測の合格条件に含める。**

変更1で素の序列のハード制約が入れば、変更2の必要性は下がる可能性がある。
**変更1を入れた状態で変更2を計測し、上積みが無ければ変更2は入れない。**

予測どおり分離は**さらに改善する**が、**共演人数が明確に落ちる**。

**トレードオフは単調で、`maxDrift` は「分離 ⇔ 多様性」を直接つなぐノブだった。**
下位帯メンバーの共演相手は、ハシゴ式で自分の帯から出ること（＝ドリフト）で
増える。ドリフトを狭めれば実力帯は綺麗に保たれるが、その帯の中に閉じ込められる。

**本 plan の出発点は「同じメンバーとの試合が多い」という感想であり、多様性を
削って分離を買う変更2は方向が逆。不採用とする。** 分離は変更1が
共演人数をほぼ落とさずに（21人3C: 13.27 → 13.26）改善しており、これで足りる。

`docs/plans/2026-07-29-ladder-drift-limit.md` が緩める方向で「悪化する」と
結論づけ、本 plan が狭める方向で「多様性を損なう」と結論づけたことで、
**`maxDrift = stepSize` は両側から挟まれた**。今後この値を動かす場合は、
分離と共演人数の両方を必ず併せて見ること。

### 変更3: 帯内の多様性強化（変更1・2の結果を見てから着手）

- `PAIR_REPEAT_PENALTY_CAP` を 0.2 → 0.6〜0.8 の範囲で振る（`SKILL_GAP_WEIGHT = 2.0`
  より必ず小さく保ち、層3が層2を越えないようにする）
- `COMBO_REPEAT_ALLOWANCE` を 2 → 1

切り分けて測った**。

**`PAIR_REPEAT_PENALTY_CAP` の sweep（`COMBO_REPEAT_ALLOWANCE` は 2 のまま）**

#### ユニットテストを追加しなかった理由

`PAIR_REPEAT_PENALTY_CAP` は**1回の選出では挙動が変わらない**統計的なノブだった。
0.2 と 0.6 で選出が分かれるケースを探したが（6人・8人で特定ペアの共演履歴を
積み上げた盤面など）、いずれも同じ4人・同じペア分けが選ばれた。効果はセッション
全体の集計にしか現れない。

無理に判別ケースを作ると、他の定数を少し触っただけで壊れる脆いテストになるため
追加していない。**この定数の回帰検出は `scripts/bench-court-assignment.ts` が担う**。
値を変える際は必ず bench で共演人数と分離の両方を確認すること。

### 変更4: 未共演を明示的に優遇（変更3の効果が不足する場合のみ）

現在のペア重複ペナルティは回数に比例するのみ。「未共演なら負のスコア、以降は回数
比例」の形にして、げん×りょーや4回のような山を崩しやすくする。**帯を跨ぐ候補には
適用しない**（層1のハード制約が先に効くので自動的にそうなる）。

#### 計測結果: 不採用（頭打ちは破れたが、分離との交換レートが悪い）

`getPairRepeatPenalty` に段差項を追加した:

```
metPairs = 6ペアのうち (partner回数 + opponent回数) > 0 のペア数（0〜6）
raw = 0.1*Σpartner + 0.05*Σopponent + PAIR_UNMET_STEP_WEIGHT * metPairs
penalty = oneGameDelta * min(raw, PAIR_REPEAT_PENALTY_CAP)
```

段差項は最大 `6 * weight` になるため cap にも余裕が要る。`(weight, cap)` を5通り計測
（`SEEDS=150 ROUNDS=15`、決定化後の bench）:

共演人数（**高いほど良い**）:

| 条件 | NOISE | (0, 0.6) 現状 | (0.05, 0.8) | (0.1, 0.8) | **(0.1, 1.0)** | (0.15, 1.0) |
| --- | --- | --- | --- | --- | --- | --- |
| 21人3C | 0 | 13.34 | 13.54 | 13.54 | **13.72** | 13.65 |
| 21人3C | 4 | 13.39 | 13.59 | 13.55 | **13.80** | 13.70 |
| 18人3C | 0 | 12.99 | 13.08 | 13.05 | **13.22** | 13.16 |
| 16人2C | 0 | 10.71 | 10.84 | 10.75 | **10.96** | 10.85 |

**頭打ちは確かに破れた。** `PAIR_REPEAT_PENALTY_CAP` の線形項だけでは 0.6 で止まって
いたが、段差項＋cap=1.0 で 21人3C が +0.38 伸びた。ペア最大重複も 2.81 → 2.72 と改善。

しかし分離%（低いほど良い）が対価になる:

| 条件 | NOISE | (0, 0.6) 現状 | (0.1, 1.0) | 差 |
| --- | --- | --- | --- | --- |
| 21人3C | 0 | 0.6 | 0.9 | +0.3 |
| 18人3C | 4 | 3.3 | 4.0 | **+0.7** |
| 16人2C | 0 | 1.9 | 2.3 | +0.4 |

**不採用の理由:**

1. **交換レートが変更3より悪い。** 変更3（cap 0.2→0.6）は 21人3C で共演 +0.26 に対し
   分離 +0.3pt だったが、変更4 は共演 +0.38 に対し 18人3C NOISE=4 で +0.7pt。
   これまでの多様性変更で最大の分離悪化。
2. **層の分離が薄くなる。** cap=1.0 は `SKILL_GAP_WEIGHT = 2.0` の半分。層3が層2に
   迫り、「多様性は実力分離を侵食しない」という本 plan の方針が怪しくなる。
3. **後述の構造分析により、そもそも伸びしろの小さい方向だと分かった**（次節）。

## 実データの再分析: 不満の実体は「共演人数」ではなかった

変更3・4 を進める過程で実データ（2026-08-04、21人44試合）を掘り直したところ、
**当初の問題B の見立てが不正確だった**ことが分かった。

### げんの共演人数は平均的で、上位者の方が悪い

| メンバー | パートナー人数 | 共演人数 | 最多相手の占有率 |
| --- | --- | --- | --- |
| げん (r20) | 7人 | 13人 | りょーや **50%** |
| りょーや (r21) | 5人 | 10人 | げん **57%** |
| ゆーや (r2) | 6人 | **8人** | きゃん **62%** |
| きゃん (r4) | 7人 | 9人 | ゆーや **62%** |
| あすか (r17) | 6人 | 11人 | 美玖 **67%** |

げんの共演13人は21人中で中位。**ゆーや（8人）・きゃん（9人）の方が悪い**が感想は
出ていない。体感に効くのは共演人数ではなく**特定の1人の占有率**だった。

### 占有率 50% は構造的な下限で、アルゴリズムは既にそこにいる（← 後述のとおり誤り）

> **この節の結論は誤り。** バンドが厳密な7人ブロックだと仮定した計算で、実効プールは
> もっと広い。下の「訂正」節を参照。ただし「体感に効くのは共演人数ではなく占有率」
> という指摘自体は正しく、変更5 につながった。

1試合の共演相手は3人、バンド内の候補は6人（7人バンド）。つまり期待占有率は
`3 / (バンド人数 - 1)`:

| バンド人数 | 期待占有率 |
| --- | --- |
| **7人（現在）** | **50%** |
| 10人 | 33% |
| 21人（帯なし） | 15% |

**実測（げん×りょーや 50%）は期待値ちょうど。** ペナルティの調整では下がらない。

この1つの事実が、本 plan で観測した現象をすべて説明する:

- 変更2（`maxDrift` を狭める）で共演人数が落ちた → バンドから出る機会を削ったから
- 変更3（cap 引き上げ）が 0.6 で頭打ちになった → バンド内で配り直しているだけだから
- 変更4（段差項）が分離を対価にしないと伸びなかった → 同じ天井を押しているから

**多様性を本質的に増やすにはバンド幅を変えるしかない**（＝分離を緩める）。
これらのペナルティは同じトレードオフ曲線上を動いているだけで、曲線そのものは
動かせない。

### ランク基準のバンドは、今回のメンバー構成と噛み合っていない

現在の実力判定（`getSkillGapPenalty` / `hasTopBottomExtremes`）は**ランク距離**で、
実際のレート差を見ていない。現在のバンドのレート幅:

| 帯 | 範囲 | レート幅 |
| --- | --- | --- |
| 上位 (r1-7) | 37.02 〜 30.86 | 6.16 |
| 中位 (r8-14) | 30.11 〜 24.62 | 5.49 |
| **下位 (r15-21)** | 24.37 〜 15.35 | **9.02** |

**下位帯が最も実力差が open なのに、最も閉じ込められている。** りょーや（15.35、
次点との差 4.22 = 全体で断トツの外れ値）のせい。

ランク基準は「ソンシズ↔あすか（レート差 0.10）」と「げん↔りょーや（1.58）」と
「みずき↔りょーや（6.45）」をすべて“隣接”として同じに扱う。

レート差 ±6.0 でプールを決めた場合の人数（現在はどの人も6人）:

| メンバー | 現在 | レート基準 ±6.0 |
| --- | --- | --- |
| やっちゃん・もえこ・ゆきえ (r8-10) | 6人 | **13人** |
| マツオ〜美玖 (r11-15) | 6人 | **12人** |
| ソンシズ・あすか (r16-17) | 6人 | **10人** |
| げん (r20) | 6人 | 7人 |
| りょーや (r21) | 6人 | **2人** |

密なレート帯ではプールが倍増する。**実力差を一切広げずに多様性だけ増える**区間で、
占有率は 50% → 27〜33% になる計算。一方 りょーや は正直に「近い実力が2人しかいない」
と出る。これはアルゴリズムの問題ではなく**メンバー構成の問題**として扱うべき。

### レート差ベースの案は不採用（着手前に取り下げ）

`getSkillGapPenalty` の許容幅をランク距離からレート差へ移す案を検討したが、
**初期レートは序列を決めるための人手の値で、間隔が校正されていない**。
`ordering` → `skill` へ改名した経緯（`docs/plans/2026-07-29-rating-vocabulary.md`）
のとおり順序を決める道具であり、差を距離として扱う根拠がない。今回のデータでも
スコアの大半が `100-99` の勝敗マーカーで、実点数は8試合分しかなく間隔を検証できない。
レートの外れ値を考慮し始めると調整がきりがないため取り下げた。

### 訂正: 占有率50%は「構造的下限」ではなかった

上の「バンド7人 → 期待占有率 50%」は**バンドが厳密な7人ブロックだと仮定した計算で、
実態と合っていなかった**。実データのランク距離ごとの共演回数を見ると距離8まで
平均1回以上あり、ハシゴ式のシャッフルで実効プールはブロックより広い。ブロック境界
（r7|r8、r14|r15）にも段差は出ていない。げんの共演相手も実際13人いる。

「自分が実際に共演した人数に均等配分した場合の上限」と比べると:

| メンバー | 最多相手 | 観測 | 均等配分なら | 超過 |
| --- | --- | --- | --- | --- |
| 美玖 (r15) | あすか | 6回 | 3回 | **+3** |
| あすか (r17) | 美玖 | 6回 | 3回 | **+3** |
| ゆーや (r2) | きゃん | 5回 | 3回 | +2 |
| げん (r20) | りょーや | 4回 | 2回 | +2 |
| みずき (r18) | あすか | 5回 | 3回 | +2 |

**21人中19人で超過が出ている。構造的下限ではなく、単に均せていない。**

### 変更5: 特定の1人への偏りのペナルティ（集中度）— 採用

`getPairRepeatPenalty` は6ペアの回数を**合計**して上限を掛けるため、
「1人と6回、他は0回」と「3ペアが2回ずつ」が同じ評価になる。避けたいのは前者だけ
なので、6ペアのうち**最も顔を合わせているペア**の回数に別枠でペナルティを掛ける。

```
penalty = min(合計ベース, PAIR_REPEAT_PENALTY_CAP=0.6)
        + min(PAIR_CONCENTRATION_WEIGHT * 最多ペアの共演回数, PAIR_CONCENTRATION_CAP)
```

均等に散っている組には加算されない。**順位もレートも使わず履歴だけで決まる**ため、
手動レートの間隔が校正されていないことに影響されない。

bench に「最多相手の占有率」（1人あたり `max(共演回数) / 自分の試合数` の平均）を
指標追加して計測した。`(WEIGHT, CAP)` を8通り sweep:

| 条件 | NOISE | 指標 | 変更前 | (0.05,0.4) | **(0.1,0.6)** | (0.15,0.6) | (0.2,0.8) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 21人3C | 0 | 占有率% ↓ | 47.2 | 46.0 | **45.2** | 45.0 | 44.6 |
| 21人3C | 0 | 分離% ↓ | 0.6 | 0.7 | **0.8** | 0.9 | 0.7 |
| 18人3C | 4 | 占有率% ↓ | 48.7 | — | **47.0** | 46.7 | 46.4 |
| 18人3C | 4 | 分離% ↓ | 3.3 | — | **3.6** | 3.8 | 4.1 |
| 16人2C | 0 | 占有率% ↓ | 61.4 | 59.4 | **58.3** | 57.1 | 56.0 |
| 16人2C | 0 | 分離% ↓ | 1.9 | 2.1 | **2.1** | 2.4 | 2.3 |

6条件平均の分離悪化は WEIGHT=0.1 までが +0.08pt、**0.15 以上で +0.30pt へ加速する**。
占有率の改善／分離の悪化の比は WEIGHT≤0.1 が約 -23〜-26、0.15 以上が約 -7〜-11 と
明確に落ちる。よって **WEIGHT=0.1** を採用。CAP は 0.4 と 0.6 で分離のコストが同じ
（6条件平均 +0.083pt で一致）なので、6回目まで効き続ける **0.6** を採る。

**変更3・4 と決定的に違うのは、これが別の軸を叩いていること。** 変更3（合計の上限
引き上げ）と変更4（未共演の段差）はどちらも共演人数を分離と交換していたが、変更5 は
分離ほぼ据え置きで占有率を 1〜3pt 下げる。診断（合計ベースでは偏りを検出できない）
どおりの結果になった。

#### ユニットテスト

`assignCourts - 特定の1人への偏りのペナルティ（集中度）` を追加。

合計ベースのペナルティが上限に張り付く盤面を作る: 待機5人のうち p0-p1 が6回
パートナー（最多ペア=6回）、p2/p3/p4 は互いに2回ずつ（合計は同程度だが最多ペア=2回）。
**集中度ペナルティが無いと 6回組んだ p0+p1 がそのまま再選出される**ことを確認済み
（`WEIGHT=0` にすると3回とも落ちる）。変更3・4 の定数と違い、この項は単一の選出で
挙動が変わるためテストで固定できる。

## 計測（bench）

### bench を作り直してリポジトリに入れる

`docs/plans/2026-07-29-ladder-drift-limit.md` が使った `scratchpad/truth.ts` は
scratchpad に置かれたため**現存しない**。同じハーネスを
`scripts/bench-court-assignment.ts` として**リポジトリにコミットする**（同じ計測を
毎回作り直さないため）。

既存の `scripts/simulate-court-assignment.ts` は `src/lib/algorithm.ts` を
import せずロジックを再実装した独立シミュレータで、本番の変更を計測できない。
本 bench は **`assignCourts` / `formTeams` を実際に呼ぶ**。

ハーネスの要件（`truth.ts` と同じ、循環計測を避けるため）:

- 各プレイヤーに**真の実力** `trueRank` を持たせる
- `player.rating` は `trueRank + ノイズ(±NOISE順位)` を並べ直した写し
  （＝手動序列が古い状況を再現）
- 勝敗は `trueRank` から Bradley-Terry で確率的に決める
- **分離の評価は `trueRank` 基準**で行う（`player.rating` を正解にすると、序列を
  動かす仕組みは必ず悪化して見える）

`player.rating` を正解として測る既存の `focus.ts` / `gbench.ts` 系の見方は使わない。

### 条件

- `SEEDS=150`、`NOISE ∈ {0, 4, 8}`
- 人数・コート数: `[13,2], [14,2], [16,2], [15,3], [18,3], [21,3]`
  （21人3コートは今回の実セッション条件なので追加する）
- `mode='mixed'`（コート終了時刻が最大60秒ずれるまで同時扱い）

### 指標

| 指標 | 意味 | 方向 |
| --- | --- | --- |
| 分離 | 真の上位3人×下位3人が同コートに入る割合 | 低いほど良い |
| 真の実力差 | 4人の `trueRank` の最大−最小 | 低いほど良い |
| 試合数幅 | 最多試合数 − 最少試合数 | 低いほど良い |
| 回転 | 1人が経験するコート数 | 高いほど良い |
| **共演人数** | 1人あたりの異なる共演相手数 | **高いほど良い** |
| **ペア最大重複** | 同一ペアの最大再演回数 | **低いほど良い** |

下2つは本 plan で追加する（多様性を測る指標が既存 bench に無いため）。

### 合格条件

- 変更1: 分離が改善し、試合数幅の悪化が +0.3 未満、回転の低下なし
- 変更2: 変更1適用済みの状態から分離がさらに改善し、**回転の低下なし**、
  試合数幅の悪化が +0.3 未満
- 変更3・4: 共演人数が増え、ペア最大重複が減り、**分離・試合数幅・回転が悪化しない**

いずれも満たさなければその変更は入れず、否定的結果を本 plan に追記する
（`ladder-drift-limit` と同じ扱い）。
